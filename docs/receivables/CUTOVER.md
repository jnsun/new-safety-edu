## 操作原则

- 指定一名操作人和一名复核人；逐项记录开始/结束时间、发布版本和不含敏感信息的证据。
- 任一步出现未预期错误、数据计数不一致、权限越界、审计缺失或备份不可恢复，立即停止，不继续下一步。
- 旧 `/ledger/` 在新入口验证完成前保持原状；开始流量切换后，旧系统保持只读，不允许新旧两套写路径并存。
- 回退必须同时恢复应用版本、PostgreSQL 和 uploads 的同一时间点快照。

## 单一有序运行簿

1. **确认准入条件并冻结变更。** 核对正式 50,000/500,000 容量门、完整有序 FINAL 和桌面/窄屏七角色浏览器验收均有当次发布版本的新鲜 PASS 证据。冻结旧台账写入和数据库结构变更，记录最后写入时间。任一证据缺失或冻结失败则停止。

2. **核对目标运行时。** 在目标主机运行 `node --version` 和 `psql --version`，必须分别为 Node.js 22.x 与 PostgreSQL 16.x；核对 `pnpm` 锁定安装、磁盘空间、数据库连接、上传目录权限和反向代理配置。版本或资源不符则停止。

3. **备份并验证可恢复性。** 对目标 PostgreSQL 做一致性备份，对 uploads 做同一时间点的完整备份，生成校验和并在隔离位置完成恢复抽查。记录备份标识和校验结果，但不记录连接秘密。备份失败、校验不一致或恢复抽查失败则停止。

4. **部署不可变应用版本。** 将已验收的精确提交部署到预发布槽位，使用锁文件安装依赖并运行构建；尚不开放 `/receivables`，也不更改 `/ledger/`。构建、配置校验或进程启动失败则停止并恢复上一应用版本。

5. **在空库验证迁移与种子。** 先在与目标同版本的空 PostgreSQL 16 数据库设置待发布 `DATABASE_URL`，依次运行：

   ```powershell
   pnpm db:validate
   pnpm db:deploy
   pnpm db:bootstrap
   ```

   必须确认迁移只前进一次、种子可重复执行、初始财务部门和业务字典计数符合发布证据。任何漂移、失败或重复数据均停止；不得在失败状态下对生产库重试未知命令。

6. **迁移目标库。** 在写入冻结和备份已验证的前提下，对目标库运行 `pnpm db:deploy`，再运行 `pnpm db:bootstrap`。核对迁移历史、约束和索引均与已验收版本一致。若失败，停止应用启动并执行第 14 步回退。

7. **绑定财务组织。** 由获授权的公司管理员通过主系统恢复入口选择财务资产组织；不得直接改表或在命令中硬编码生产 ID。负责人随后登录，确认系统显示待配置状态正确。绑定对象错误、入口越权或状态不一致则停止并回退。

8. **负责人复核并确认配置。** 负责人逐项复核财务归属部门、部门启停状态、业务字典及默认值，完成服务端确认动作。保存前复核部门代码唯一性；确认后重新登录并验证访问事实。任何项目缺失、重复或确认状态不一致则停止。

9. **运行隔离角色矩阵 smoke。** 仅在专用隔离数据库和专用本机端口执行 `pnpm smoke:receivables-e2e`；不得把 smoke 指向目标生产库。核对负责人、财务管理员、两个不同部门报账员、只读、查看全部和公司管理员七个独立会话的允许/拒绝、撤权即时生效、无副作用、审计、文件、导入和导出结果，并确认清理为零残留。任一断言失败则停止。

10. **开放新入口。** 在反向代理或发布路由中启用主系统 `/receivables`，先仅允许切换复核人访问。验证登录沿用主系统会话，门户、看板、台账和财务侧栏均来自同一应用/API；不得创建独立登录页、浏览器数据库连接或 token URL。健康或权限检查失败则关闭新入口并停止。

11. **执行发布后检查。** 用受控测试数据依次验证 `/api/health`、一笔台账读写与乐观锁冲突、跨部门拒绝且无副作用、私有附件上传/下载/hash/拒绝及 `file.read` 审计、后台导出完成与一次性 POST token 下载。核对关键变更审计和失败审计可检索，uploads 中对象与数据库元数据一致。任何 5xx、越权、审计缺口、文件不一致或导出截断均停止并进入回退。

12. **切换旧入口。** 发布后检查全部通过后，将旧 `/ledger/` 原子重定向到主系统登录页或 `/receivables`；旧服务继续禁止写入。验证未登录用户先登录、已登录有权用户到新入口、无权用户看不到财务数据，并确认不存在重定向循环。

13. **观察并结束窗口。** 在约定观察期持续检查 API 健康、错误率、数据库连接、慢查询、审计写入、文件读取和导出任务。观察期无异常后记录切换完成；旧运行代码和嵌套 Git 的归档或删除必须另行批准，不属于本次切换。

14. **停止、判定并执行获批处置（任一停止条件触发时）。** 必须严格按以下顺序执行，任何人不得先覆盖当前 PostgreSQL 或 uploads：

    1. 立即冻结新旧两套写入，关闭 `/receivables` 流量并撤销 `/ledger/` 重定向；停止会产生后台写入的任务。只允许只读取证和备份。
    2. 对故障当下的 PostgreSQL 与 uploads 制作同一时间点的保护副本并生成校验和；同时保存当前应用版本、迁移历史、审计日志和切换窗口操作日志。保护副本验证失败则保持全冻结并升级处理。
    3. 以第 3 步切换前备份为基线，核对切换窗口内是否存在新台账、金额、附件、导入、导出或审计事实，并形成差异清单。不得通过启动旧系统写入来“试探”数据。
    4. 由数据负责人基于差异清单书面选择“在当前版本前向修复”或“回退到切换前备份”，并明确切换窗新写入的保留、导出、重放或作废方式。在书面选择和复核人批准前，不得恢复应用、数据库或 uploads。
    5. 若选择前向修复，只在当前保护副本可恢复的前提下实施获批修复并重做第 11 步检查；不得恢复旧备份。若选择回退，先按书面方案保存或导出获批保留的新事实，再停止新版本进程，恢复上一应用版本，并从第 3 步同一时间点备份成套恢复 PostgreSQL 与 uploads；禁止只恢复其中一项或双写合并。
    6. 核对处置后的应用版本、迁移版本、台账计数、文件校验和、入口行为和审计。验证失败则继续保持新旧写入冻结并升级处理；全部通过且数据负责人书面放行后，才可开放获批入口。
