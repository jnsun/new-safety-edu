# 安全生产管理平台功能与需求审查

日期：2026-09-14

审查基线：`e8b557a` 及当前工作区内已确认的 `CONTEXT.md` 业务规则

审查范围：培训教育、野外项目报送、资质证照管理，以及三者共用的人员、账号、组织、项目、权限、文件和消息能力

## 1. 审查结论

当前代码已经具备三个正式模块的可操作骨架，培训教育的普通人员主链路完成度最高；平台首页九宫格、按模块切换的侧栏、小程序四个主 Tab、私有文件和基础权限框架也已经存在。

但当前实现尚不能认定为满足本次确认后的生产业务基线。主要原因不是页面缺少，而是人员与账号合并、唯一主组织、角色恢复、项目范围、月报留痕和证照历史等关键约束仍只依赖接口约定，部分现有代码还会物理删除业务记录或账号。必须先修复共享主档和权限边界，再继续完善三个模块。

本次只验收以下三个模块：

1. 培训教育；
2. 野外项目报送；
3. 资质证照管理。

其余六个九宫格项目仅保留“待规划”卡片，不计为当前缺陷，也不提前建设。整个系统只记录安全管理事实、状态和待处理动作，不产生“可上岗”“禁止上岗”或准入资格结论。

## 2. 已确认的统一领域边界

### 2.1 共享主档

- 人员、账号、组织和项目只维护一套，三个正式模块只能引用，不得复制业务主档。
- 一名自然人只对应一个系统账号；密码、已验证手机号和微信是同一账号的不同登录方式。
- 每人只能有一个当前主组织。项目成员关系独立，不改变主组织。
- 公司为唯一根组织，人员不能直接归属公司根。
- 经营实体和部门都直接隶属公司；只有经营实体可以创建和负责项目、开展月报。
- 外协单位只关联外协人员，不拥有内部管理权限。
- 部门人员不得加入项目；经营实体人员、外协人员和临时个人可以按规则加入项目。

### 2.2 六类角色

系统只保留六类技术角色：公司管理员、组织负责人、组织管理员、野外项目报送人员、项目管理员、普通人员。

“组织负责人”根据组织类型在界面显示为“经营实体负责人”或“部门负责人”，每个组织只能有一名当前负责人；组织管理员可以有多名。经营实体负责人/管理员可以处理本实体项目和月报，普通部门负责人/管理员不具备项目或月报权限。

### 2.3 历史与审计

- 有业务引用的人员只能停用，不能删除。
- 账号冲突不得自动删除；只有完全空账号可以事务合并，其余必须发起账号合并申请。
- 更换组织负责人、调换主组织、角色撤销、月报更正、证照更正和考试解锁都必须保留历史。
- 已完成培训、考试、签字、现场确认、有效证照历史和月报历史不得物理删除。
- 身份证号和证书编号默认脱敏；查看完整值需要再次验证、短时显示并记录审计。

## 4. 整改顺序

### 阶段 1：身份、组织与权限基础

目标：先消除会删除账号、产生双主组织、恢复旧权限或跨范围授权的生产风险。

- 建立统一人员关系变更服务和数据库约束；
- 建立空账号合并与账号合并申请；
- 统一人员停用/启用、会话撤销和角色历史；
- 落实组织类型、唯一负责人、项目责任实体和项目成员边界；
- 完成六页签人员详情与受审计敏感资料显露；
- 为高风险操作增加最小隔离数据库集成检查。

通过条件：一人一账号、一人一个当前主组织、组织一名当前负责人、跨组织/跨项目访问被 API 拒绝，现有历史不丢失。

### 阶段 2：培训教育闭环

目标：把当前最成熟模块修到规则由后端强制、历史不可漂移。

- 显式自动下发默认配置；
- 强制三级教育和项目入场考试；
- 固化批次试题版本快照；
- 收紧下发集合和管理员 scope；
- 完成解锁、辅助签字、现场确认、线下培训、提醒和报表缺口。

通过条件：自动任务幂等，批次内容不随题库变化，考试/补学/解锁/签字/确认不可由客户端伪造，五类报表字段和权限正确。

### 阶段 3：野外项目报送

目标：把当前单表 CRUD 改为保留业务历史的月报记录系统。

- 扩充唯一项目主档并保存提交快照；
- 引入 submitted/withdrawn/voided 生命周期；
- 保存修改前摘要和提交版本；
- 以部分唯一约束保证“项目+月份只有一份有效月报”；
- 完成报送实体、代办、无项目确认、附件、截止日和提醒。

通过条件：撤回、修改、重新提交和作废均可追溯；作废后可重报；公司和各范围角色权限与确认规则一致。

### 阶段 4：资质证照管理

目标：保留证照事实和年度培训历史，不产生资格判断。

- 统一证照生命周期并移除重复活动状态；
- 配置证照类型是否需要年度培训；
- 建立逐证照、逐自然年的培训状态和不可删除记录；
- 完成分级权限、导入冲突处置、号码显露审计和到期提醒。

通过条件：换证、撤销、作废、培训记录更正均保留历史；范围内可见可写；提醒去重；无任何上岗结论。

### 阶段 5：界面与外部能力收口

目标：在领域和权限稳定后完成导航、列表、移动端和外部登录体验。

- 完成人员详情页签和各模块最终菜单；
- 主档页面采用无分页/分组收起，业务历史采用服务端分页；
- 对三个正式模块做中文状态、空状态、打印和响应式收口；
- 配置真实短信网关和微信开放平台后再启用相应入口；
- 六个待规划模块继续保持不可进入。

通过条件：Web 与小程序主流程人工验收完成，外部认证无 Mock，敏感信息不进入客户端包或日志。

## 5. 每阶段发布约束

1. 开始前备份生产 PostgreSQL 和 uploads；
2. migration 只在开发库生成并纳入 Git，生产只执行 `prisma migrate deploy`；
3. 禁止 `migrate reset`、`db push`、`migrate dev` 和 `docker compose down -v`；
4. 先完成 TypeScript、受影响构建、Prisma 校验和关键 API 最小检查；
5. 涉及权限或状态转换时，使用隔离 PostgreSQL 和不同真实测试角色验证允许与拒绝路径；
6. 每个阶段单独提交、部署和回归，不把五个阶段合并为一次高风险发布；
7. 不读取或改动旧项目，不把生产密钥、证件号码、手机号、照片或导入文件写入 Git 和普通日志。

## 6. 当前最高优先级缺陷

在任何新业务开发之前，应先处理以下问题：

1. 手机号/微信身份冲突会物理删除账号；
2. 管理员直接调整组织不会结束旧活动关系；
3. 人员重新启用可能继续获得旧管理权限；
4. 组织负责人唯一性和项目/组织类型边界没有数据库级保证；
5. 月报与无项目确认存在物理删除，且公司管理员代办权限与确认规则冲突；
6. 证照年度培训记录允许物理删除，证照状态存在双重权威来源；
7. 自动培训依赖“第一套模板/试卷”，批次试题未按确认规则冻结。

这些属于生产数据完整性或越权风险，优先级高于界面美化和新增功能。

## 7. 审查边界

本文件是基于代码、Prisma schema、现有构建检查和逐项业务确认形成的静态审查结论，不等同于生产数据库数据审计、微信平台验收或全部运行时权限测试。实施整改时仍需针对每个阶段重新读取真实数据库迁移状态、生产配置和部署版本。
