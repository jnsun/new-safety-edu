# 人员、账号与权限专项审查

日期：2026-09-15

审查基线：当前 `main` 工作区、Prisma schema、API、Admin、小程序，以及已写入 `CONTEXT.md` 的逐项确认规则。

审查性质：静态代码与需求一致性审查。本文件不是生产数据库数据审计，也不代表整改已经完成。

## 1. 结论

> 实施进度（2026-09-15）：阶段 A 的兼容模型和前向迁移已在隔离空 PostgreSQL 验证；阶段 B 已补齐账号基础生命周期、Person 角色主体、待激活授权和项目管理员自动入组。阶段 C 已完成设备级可撤销会话、refresh 轮换与复用失效、当前/全部设备退出、登录方式受控解除、Web 自动刷新，以及小程序账号安全摘要。账号/人员合并工作台、关系变更服务和敏感导出等后续项目仍未完成，也尚未部署。

当前系统已有人员档案、账号创建、密码重置、角色授予/撤销、微信/手机号登录、绑定申请、人员停用和基础范围鉴权，但尚未达到本轮确认后的人员与账号管理基线。

最关键的问题不是缺少几个按钮，而是当前数据库仍把管理角色绑定到账号、项目成员不能保留多段历史、关键唯一约束主要依赖应用代码、账号和人员生命周期规则不完整。直接补“修改、删除、停用”按钮会把这些风险暴露到生产，因此应先完成数据模型和服务端规则，再开放完整界面。

风险分级：

- **P0**：可能产生越权、身份错绑、历史破坏或无法安全迁移，必须先修复。
- **P1**：核心管理流程缺失或与已确认规则冲突，应在账号工作台上线前完成。
- **P2**：可用性、安全运营和审计完善项，可随同一专项收口。

## 2. 已确认的目标边界

### 2.1 人员与账号

- 人员代表现实中的自然人和业务档案；账号只代表登录身份。
- 一个人员最多关联一个当前有效账号；同一账号可同时使用用户名密码、已验证手机号和微信登录。
- 创建人员不自动创建账号；本人首次验证或管理员明确开通时才创建。
- 人员状态为待审核、正常、已停用、已合并；账号状态为待审核、正常、已停用、已合并。
- 单独停用账号不撤销角色和业务关系；停用人员则结束当前管理角色、项目关系和未完成任务。
- 人员重新启用只恢复普通人员能力，管理角色不自动恢复。
- 有历史引用的人员或账号不得物理删除；只允许删除完全无引用的误建空记录。
- 重复身份走账号合并或人员合并，源记录永久保留为已合并并指向目标记录。

### 2.2 组织、项目和角色

- 公司为唯一根组织；人员不能直接归属公司根。
- 每人只有一个当前主经营实体或部门；外协单位不是正式员工主部门。
- 管理角色在业务概念和数据库中授予人员，由其唯一有效账号行使。
- 普通人员能力由 active 人员和 active 账号自然获得，不再依赖手工 `learner` 角色。
- 一个组织只有一名当前负责人；组织管理员可有多名。
- 经营实体可以负责项目；普通部门人员不得加入项目或担任项目管理员。
- 项目管理员自动成为该项目成员；撤销项目管理员不自动结束成员关系。
- 公司管理员、组织负责人、组织管理员、报送人员、项目管理员的授权矩阵以 `CONTEXT.md` 为准。

### 2.3 敏感资料

- 姓名、手机号、照片和主部门在有权页面直接显示；身份证默认脱敏。
- 完整身份证通过绑定账号、目标人员、字段和动作的五分钟敏感授权查看并审计。
- 项目管理员可在授权项目内查看成员完整手机号，并按敏感显露流程查看完整身份证。
- 公司、组织和项目范围管理员可以生成各自范围的敏感资料包；无需另填用途或再次验证，但必须显式确认、使用当前有效会话、严格校验范围并记录审计。
- 敏感资料包可以包含照片、签字、证照附件、培训/考试/审批附件和范围内审计详情，但不得包含密码、哈希、密钥、token、openid、unionid 或原始网络安全数据。

## 3. P0 缺口

| 编号 | 当前实现 | 与目标规则的冲突 | 必须整改 |
| --- | --- | --- | --- |
| P0-01 | `RoleAssignment` 以 `accountId` 为必填主体 | 无账号人员不能获得待激活授权，账号合并会牵动业务授权，角色不是真正授予人员 | 增加 `personId` 为权威主体，迁移现有角色；账号只用于行使权限 |
| P0-02 | `PersonStatus` 无 `merged`，Person 无 `mergedIntoId` | 无法保留受控人员合并历史 | 增加已合并状态、目标关系、合并时间和操作者；禁止源记录再参与业务 |
| P0-03 | 主组织、当前负责人、活动角色等约束主要靠服务代码 | 并发或旁路写入可产生双主部门、双负责人、重复角色 | 使用 PostgreSQL 部分唯一索引和事务校验固化关键约束 |
| P0-04 | `ProjectMember` 对 `(projectId, personId)` 永久唯一 | 退出后无法建立新一段加入历史，只能覆盖旧关系 | 改为多段历史关系，并对当前待审核/有效关系做部分唯一约束 |
| P0-05 | 人员重新启用会重新授予 `learner`，且可能自动下发三级教育 | 与“普通能力不依赖 learner、重新启用不自动恢复管理角色或重新培训”冲突 | 删除新业务对 learner 的依赖；重新启用只恢复普通登录能力 |
| P0-06 | 登录、角色和范围检查没有统一要求关联 Person 当前为 active | 仅账号 active 可能继续行使权限 | 每次授权统一校验 Account、Person、角色和 scope 当前有效 |
| P0-07 | 多个关键写操作先提交业务，再以 fallback 方式记审计 | 审计失败时高风险业务仍成功 | 身份、角色、组织、合并、敏感导出等关键操作必须与审计同一事务，审计失败整体回滚 |
| P0-08 | 通用 `canAccessPerson` 被多个资料/文件端点复用 | 项目管理员可能读取与项目无关的人员证照、签字或附件 | 拆分按业务对象和动作的授权，不用“能看人员”推导“能看所有人员文件” |
| P0-09 | 敏感 token 只绑定账号和用途 | 取得一次 token 后可能被用于其他人员或字段 | token 绑定账号、目标人员、字段、动作、scope 和过期时间，并在读取时重新鉴权 |
| P0-10 | 账号/绑定冲突和合并仍有删除、直接迁移或弱查重路径 | 可能丢失身份绑定历史或产生错误归并 | 仅允许完全空账号事务合并；其余创建合并申请并逐项处置凭据、角色和历史 |

## 4. P1 缺口

### 4.1 数据模型与约束

1. `Account` 缺少“首次登录必须修改密码”标志、用户名历史、登录失败保护和最近登录元数据。
2. 用户名目前按数据库默认规则唯一，未落实统一小写、4—40 位规则和旧用户名永久保留。
3. `Person.phone` 缺少明确规范化字段及已确认范围内的活动唯一约束。
4. `WechatBinding` 只能保证 AppID + openid 唯一，不能保证同一账号在同一 AppID 下只有一个当前有效绑定。
5. `RefreshSession` 缺少设备/客户端、会话族、轮换链和重放检测字段。
6. `ChangeRequest` 缺少稳定 `requestKey`、`withdrawn` 和 `failed` 状态，以及完整的处理摘要字段。
7. `AuditLog` 缺少请求 ID、操作者角色/scope、结果、失败原因、前后摘要等结构化字段。
8. 当前合同仍包含需要手工授予的 `learner`，人员创建合同仍强制要求身份证和照片，与允许资料不完整的正式员工 active 规则冲突。

### 4.2 账号生命周期 API

当前已具备创建账号、管理员重置密码和本人修改密码，但缺少或不完整：

- 编辑用户名并填写原因；
- 停用/启用账号；
- 查询并解除某一种登录方式；
- 关闭/恢复用户名密码登录；
- 注销当前设备与注销全部设备两种动作；
- 删除误建空账号的服务端资格检查；
- 账号合并申请、审批和事务合并；
- 必须修改临时密码的受限会话；
- 最后一个公司管理员、当前操作者和唯一后台登录方式保护；
- 账号安全详情、登录历史和当前会话列表。

密码登录当前只发放约十五分钟 Cookie，没有独立 Web refresh 会话，无法实现已确认的八小时 Web 会话及安全轮换。当前 logout 会使账号全部会话失效，尚未区分“退出当前设备”和“退出全部设备”。

### 4.3 角色授权 API

- 角色接口仍接收 `accountId`，不能选择尚未开通账号的人员并创建待激活授权。
- 组织负责人和组织管理员的转授权能力没有按组织类型准确区分。
- 项目管理员跨经营实体授权申请、目标实体负责人审批尚未建立。
- 授予项目管理员时没有在同一事务中确保其成为当前项目成员并触发幂等项目入场教育。
- 更换负责人没有“新账号激活后再结束旧负责人”的待激活切换机制。
- 撤销角色缺少必填原因；部分路径没有当前操作者、最后公司管理员和会话失效保护。
- 人员调动、停用、项目结束对相关角色的自动结束规则未完整统一。

### 4.4 人员与组织关系 API

- 管理员直接调整主组织未统一结束旧关系并保留变更历史。
- 调动通过后的角色结束、项目关系处理和通知规则未完整落实。
- 公司管理员直接调整、目标负责人审批、来源负责人通知尚未共用一个领域服务。
- active 正式员工资料完整度应独立显示；现有创建校验把身份证和照片作为绝对必填。
- 项目成员六状态、退出申请、重新加入、沿用历史培训理由及批量逐行结果未完整实现。
- 现场确认需要服务端阻止本人确认；公司管理员只读，不能代确认。

### 4.5 认证与绑定

- 用户名没有统一规范化，密码登录缺少账号/IP 失败限速和临时锁定。
- 手机验证码虽有五分钟和尝试次数，但缺少完整的 IP/日限额、验证码用途隔离和旧验证码失效规则。
- 手机登录在匹配档案后可能直接创建 active 账号，应先完成身份审核条件并遵循 pending/active 规则。
- 微信网页登录没有严格限制为具备后台访问能力的人员，也未实现“先用户名密码登录，再绑定微信”的首次绑定流程。
- `/api/me/profile` 直接返回本人完整身份证，未走已确认的敏感显露授权。
- 生产/公网测试环境必须继续禁止 Mock 和万能验证码。

## 5. Admin 界面缺口

目标入口固定为：

`人员与账号` → `人员档案` / `账号与权限` / `申请与审核`

### 5.1 账号与权限

当前列表主要只有用户名、状态、角色和重置密码，需补：

- 关联人员、主组织、人员状态、资料完整性；
- 账号中文状态；
- 脱敏验证手机号、微信是否绑定、用户名密码是否启用；
- 创建时间、最近登录时间；
- 服务端返回的可执行动作；
- 编辑用户名、重置密码、停用、启用、管理登录方式、合并、删除误建空账号、查看审计；
- 公司管理员完整操作；组织负责人/管理员只读本组织状态并发起开通；项目管理员只在项目成员中看“已开通/未开通”。

账号列表不直接编辑角色。角色统一在人员详情“角色权限”页签处理，避免一套角色在两个页面出现不同规则。

### 5.2 人员详情

应固定为八个页签：

1. 基本档案；
2. 账号与微信绑定；
3. 组织与项目；
4. 角色权限；
5. 证照；
6. 培训记录；
7. 申请记录；
8. 审计记录。

页面按钮不能仅根据前端角色推断，应由服务端返回当前对象的操作能力。完整身份证显露必须调用绑定目标和字段的敏感授权；项目管理员完整手机号只在项目成员语境内显示。

### 5.3 申请与审核

当前主要覆盖绑定、注册、资料修改和部门调换，需统一展示但使用独立处理器：

- 账号开通；
- 微信/手机号绑定与换绑；
- 账号停用建议；
- 账号合并、人员合并；
- 身份资料更正、人员重新启用；
- 主组织/内部责任实体变化；
- 项目加入、退出；
- 跨经营实体项目管理员授权。

同一 active pending 请求由数据库 `requestKey` 唯一约束；重复提交返回已有申请，不以列表隐藏重复记录代替幂等。

## 6. 小程序缺口

当前已有登录、本人资料、照片修改、部门调换和退出登录，仍需补齐：

- 本人账号安全页：已启用登录方式、修改/验证手机号、微信换绑申请；
- “退出当前设备”和可选的“退出全部设备”；
- 本人当前管理角色、具体组织/项目 scope 和授权时间；
- 资料完整度及待处理申请；
- 本人完整身份证的短时敏感显露，不在普通资料响应中长期返回；
- 本人个人档案导出申请与安全下载；
- 临时密码只允许进入修改密码流程的明确提示（如小程序允许该账号登录）。

小程序不增加账号管理后台，不允许普通人员自行授予角色、停用账号或直接指定 `personId` 绑定。

## 7. 敏感资料导出实现要求

这是本轮确认中权限影响最大的新增能力，应作为独立高风险服务实现：

1. 客户端提交数据范围和导出类别，不提交任意数据库筛选条件。
2. 服务端从当前角色重新计算 company/org/project scope。
3. 生成异步导出任务，保存请求人、范围快照、内容类型、创建/完成/过期状态。
4. 从私有文件存储读取允许的文件，逐项核验业务对象与 scope；不允许仅凭 file ID 导出。
5. ZIP 内包含清单、生成时间、范围说明、缺失/失败项及文件 SHA-256。
6. 下载使用一次性 token，最长十分钟；首次成功下载后失效，到期后删除产物。
7. 同一账号限制并发和短时重复任务；失败必须显示准确原因，不生成不完整却标记成功的包。
8. 请求、完成、下载、过期清理全部审计；异常大范围或高频导出产生系统内安全提醒。

## 8. 建议实施顺序

### 阶段 A：数据库与兼容迁移

- 增加 Person 合并模型、角色 Person 主体、用户名历史、登录方式状态、请求幂等键和必要审计字段。
- 重构 ProjectMember 历史模型。
- 添加部分唯一索引。
- 迁移前只读扫描现有重复主组织、重复角色、重复 pending、孤儿账号和冲突绑定；发现冲突即停止，不自动修复生产数据。
- 保留旧 learner 记录为兼容数据，但新授权不再创建或依赖它。

### 阶段 B：领域服务与权限

- 建立统一账号生命周期、角色授权、主组织变更、项目成员和合并服务。
- 所有关键写操作与审计同一事务。
- 将通用人员访问拆成字段和业务对象级授权。
- 统一 sessionVersion 与 refresh session 撤销策略。

### 阶段 C：认证和登录方式

- Web refresh、会话轮换、当前/全部设备退出、临时密码强制修改。
- 用户名规范化及历史保留。
- 手机/微信绑定、换绑和冲突申请。
- 密码与验证码失败保护。

### 阶段 D：Admin 与小程序

- 完成账号工作台、八页签人员详情、统一申请中心。
- 补小程序账号安全、角色范围和敏感显露。
- 所有操作按钮消费服务端能力，不复制权限规则。

### 阶段 E：敏感导出和收口

- 完成范围化敏感资料包。
- 在独立测试 PostgreSQL 上验证迁移、允许/拒绝路径、历史保留和会话失效。
- 先部署测试站；生产部署必须再次获得明确授权，并先备份数据库和 uploads。

## 9. 最小验收清单

1. 一个 active 人员最多一个 active/待审核账号；一个账号最多关联一个人员。
2. 每人最多一个当前主组织；每组织最多一个当前负责人。
3. 没有账号的 active 人员可以获得待激活授权，但不能实际登录行使权限。
4. 账号停用立即使全部会话失效，重新启用恢复原角色；人员停用结束角色且重新启用不恢复角色。
5. 修改用户名、重置密码、解绑登录方式、角色变更后旧会话按规则立即失效。
6. 最后一个公司管理员、自身账号及唯一后台登录方式受到保护。
7. 账号或人员有历史引用时不能物理删除，合并后源记录及审计可追溯。
