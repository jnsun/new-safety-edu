# 应收账款数据处理、催收权限与台账易用性改造设计

日期：2026-09-16

状态：设计已确认，待书面规格复核

关联基线：`docs/superpowers/specs/2026-09-15-receivables-native-integration.md`

## 1. 目标

在已经原生接入主系统的“应收账款管理”模块上完成一轮聚焦改造：

- 把新增记录、Excel 导入、Excel 导出统一到“数据处理”入口。
- “生成报表”与“导出 Excel”合并为同一项能力，不再建设独立报表功能。
- 恢复迁移时遗漏的五个催收跟踪字段，并增加一个明确的报账员授权开关。
- 让字典选项改名能够事务性同步既有台账，同时保留逐条历史。
- 增加按“单位”筛选、列宽拖动、长文本展示和更紧凑的模块导航。
- 修复应收账款模块内 Modal、Drawer 的关闭与取消行为。

本设计扩展现有 React、Ant Design、Fastify、Prisma/PostgreSQL、权限、审计、私有文件、后台导出任务和用户偏好能力，不另建通用权限框架、报表引擎或催收活动子系统。

## 2. 非目标

- 不恢复浏览器直连 Supabase，不引入第二套账号或文件机制。
- 不把台账关联到主系统项目主档，也不改变独立财务归属部门模型。
- 不新建“生成报表”菜单、模板设计器、透视表或多工作表分类报表。
- 不把“允许维护催收进展”拆成逐字段权限。
- 不为本次改造增加通用可配置权限生成器或独立催收事件表。
- 不改变开票、回款、核销公式和负责人、财务管理员的既有权限。
- 不给现有报账员自动加开新能力。

## 3. 信息架构与路由

### 3.1 “数据处理”入口

应收账款模块侧栏用一个“数据处理”入口替代原来的独立导入、导出入口。页面包含三个标签页：

1. 新增记录
2. Excel 导入
3. Excel 导出

“生成报表”不再单列，它与“Excel 导出”指向同一功能。

各标签页按服务端返回的能力显示：

- 新增记录：负责人、财务管理员，或已启用 `canCreate` 的报账员。
- Excel 导入：仅负责人和财务管理员。
- Excel 导出：负责人、财务管理员，或已启用 `canExport` 的报账员/只读人员。

直接访问标签页 URL 时仍执行相同的服务端权限校验；隐藏标签页不是授权手段。保留旧导入、导出 URL 的兼容重定向，分别落到“数据处理”的对应标签页，避免旧书签失效。

### 3.2 新增记录

从台账总览顶部移除“新建台账”按钮。新增操作只在“数据处理 → 新增记录”提供，继续复用现有创建接口、字段校验和权限判断。

创建成功后跳转并打开新台账详情，不停留在空表单，也不另建第二套创建流程。

## 4. 数据模型与兼容迁移

### 4.1 恢复五个催收字段

在 `ReceivableLedger` 上做可空、向后兼容的加法迁移：

| Prisma 字段 | 数据库列 | 页面名称 | 类型 | 字典 |
| --- | --- | --- | --- | --- |
| `dunningDate` | `dunning_date` | 最新催收时间 | `DateTime? @db.Date` | 无 |
| `communicationMethod` | `comm_method` | 沟通方式 | `String?` | `comm_method` |
| `counterpartyFeedback` | `feedback` | 对方反馈 | `String?` | `feedback` |
| `latestProgress` | `latest_progress` | 最新进展 | `String?` | `progress_note` |
| `nextPlan` | `next_plan` | 下一步计划 | `String?` | `next_plan` |

这五项是旧模块已有而原生迁移遗漏的字段。项目状态和附件已经存在，不重复建模。

正式环境当前没有需迁移的业务数据，因此迁移只增加可空列，不做旧值回填；若部署环境已有记录，既有行保持 `NULL`，不删除、不重写其他字段。

现有 Excel 导入模板、解析、预览和应用流程同步支持这五个字段，并兼容旧模块列名“最新催收时间/催收时间/催收日期/询证日期、沟通方式、对方反馈/反馈、最新进展/进展、下一步计划/计划”。导入更新继续使用既有事务、revision 和逐条历史机制。

### 4.2 新授权开关

在 `ReceivableAccessGrant` 增加：

- `canMaintainCollection Boolean @default(false)`，数据库列为 `can_maintain_collection`。

默认值必须为 `false`，迁移后任何现有报账员都不会自动获得新增编辑能力。财务管理员使用固定模块权限，不依赖此开关；只读角色不能启用此开关。

### 4.3 列宽偏好

沿用现有应收账款列偏好，不增加新表。在现有 `{ order, visible, frozen }` JSON 中增加 `widths` 映射：

```json
{
  "order": [],
  "visible": [],
  "frozen": [],
  "widths": { "projectName": 260, "customerName": 220 }
}
```

旧偏好没有 `widths` 时按默认列宽归一化，不能使整份偏好失效。只保存允许的列 ID 和服务端规定范围内的整数宽度。

## 5. 权限与历史

### 5.1 “允许维护催收进展”

财务授权管理为报账员增加单一开关“允许维护催收进展”。启用后，报账员仅可在自己具有 `canWrite` 的财务归属部门内修改：

- 项目状态
- 最新催收时间
- 沟通方式
- 对方反馈
- 最新进展
- 下一步计划
- 上传附件

该开关不授予新增记录、导出、查看全部或跨部门能力，也不允许编辑金额、合同编号、财务归属部门、开票、回款、核销或其他主档字段。

当前已经允许报账员维护的债权状态、清收责任人和催收备注保持现有权限规则，本次开关不扩大也不收回这三个字段。附件上传属于本次开关控制范围：未启用时不能上传，启用后仍须满足台账所属部门的写权限。

权限判定同时要求：

1. 账号和关联人员均为 active；
2. 财务授权有效；
3. 角色为报账员；
4. `canMaintainCollection = true`；
5. 当前台账所属财务归属部门具有 `canWrite = true`。

任一条件不满足时，服务端拒绝更新和附件上传。前端禁用或隐藏控件仅用于说明当前能力。

负责人和财务管理员继续拥有完整维护能力；只读人员无论其他标志如何都不能维护催收进展。

### 5.2 历史与并发

每次修改上述台账字段必须：

- 携带当前台账 revision；
- 在同一事务中写入完整 `beforeSnapshot` 的 `ReceivableLedgerRevision`；
- 写入明确的变更原因；
- 更新字段、`updatedBy` 并递增台账 revision；
- 写入关键操作审计。

revision 不匹配返回 409，不自动覆盖他人修改。附件仍使用现有私有文件模型；上传、下载和作废沿用既有鉴权与审计，不把二进制内容写入台账 revision。

## 6. 字典选项改名与台账同步

### 6.1 行为

修改一个已被台账引用的字典选项时，不再只阻止改名。系统先返回影响预览，用户确认并填写原因后，在一个数据库事务内：

1. 锁定源字典选项以及受影响台账，重新核对 revision 和影响指纹；
2. 为每条受影响台账写入变更前完整快照；
3. 把匹配旧值的台账字段改为新值并逐条递增 revision；
4. 更新字典选项本身及 revision；
5. 写入包含类别、旧值、新值、影响数量、操作者和原因的关键审计；
6. 任何一步失败则全部回滚。

改名不能用不带逐条 revision 的 `updateMany` 代替历史写入。提交前后影响集合不同、选项 revision 已变化或目标值冲突时返回 409，要求重新预览。

### 6.2 支持范围

字典类别到台账字段的映射为：

| 字典类别 | 台账字段 |
| --- | --- |
| `project_status` | 项目状态 |
| `final_method` | 决算方式 |
| `debt_status` | 债权状态 |
| `client_attr` | 客户属性 |
| `unit` | 单位 |
| `work_nature` | 工作性质 |
| `sector` | 板块 |
| `comm_method` | 沟通方式 |
| `feedback` | 对方反馈 |
| `progress_note` | 最新进展 |
| `next_plan` | 下一步计划 |

附件类别继续使用附件自己的 revision 和审计流程，不伪装成台账字段历史。

改名成功后使字典、台账列表、详情、看板、筛选项和导出元数据缓存失效，确保下一次读取立即显示新值。

## 7. Excel 导出

### 7.1 同一功能、一个文件、一张表

“Excel 导出”和原需求中的“生成报表”是同一功能。每次成功导出生成一个 `.xlsx` 文件，文件中只有一张名为“应收账款明细”的工作表；不同分类结果不拆分工作表，分类字段作为普通列保留在连续明细表中。

工作表启用冻结表头和自动筛选。没有匹配记录时不创建空导出任务，页面提示“当前条件无可导出记录”。

### 7.2 分类条件

导出页面允许使用以下受控分类字段组合筛选：财务归属部门、单位、客户属性、工作性质、板块、项目状态、决算方式、债权状态、沟通方式、对方反馈、最新进展、下一步计划和记录状态。

每个分类字段的可选值是：

- 当前用户可见记录中的实际非空值；与
- 该字段对应类别中 active 的内置字典值

的去重并集。由服务端在当前权限范围内生成，前端不能提交任意字段名扩大查询面。

同一分类条件内可多选，按“任一值匹配”；不同分类条件之间按 AND 组合。所有条件继续叠加服务端当前可见财务归属部门范围，`canViewAll` 只能来自服务端授权。

### 7.3 列选择与预览

服务端提供导出预览，返回：

- 当前权限及分类条件下的匹配记录数；
- 允许导出的字段清单；
- 每个字段在匹配集合中的非空记录数。

前端据此默认选择至少有一条非空值的字段；匹配集合中全空的字段默认不选，但用户仍可主动选择。用户必须至少选择一列才能提交导出。

服务端只接受固定字段白名单，并重新执行权限、条件和列校验。导出任务保存不可变的权限范围、分类条件、列清单及其预览基准；任务执行时不相信前端传来的标签、SQL 或部门范围。

导出审计至少包含操作者、权限范围快照、筛选快照、列清单、匹配行数、文件 SHA-256 和任务结果。后台任务、一次性下载令牌、过期清理和私有文件存储沿用现有实现。

## 8. 台账总览与布局

### 8.1 按“单位”筛选

台账总览增加单选“单位”筛选，绑定现有 `creditorUnit` 查询字段。选项为当前可见记录中的实际非空单位与 active `unit` 字典值的去重并集；选择一个值后由服务端筛选、计数和分页。

该筛选不得改变用户可见的财务归属部门范围。清空筛选恢复原结果。

### 8.2 可调列宽与长文本

台账表头提供拖动手柄，允许调整每个可见列的宽度：

- 拖动过程即时反馈，结束后写入现有列偏好；
- 宽度必须受每列最小/最大值约束，防止列消失或无限扩张；
- 项目名称、客户名称默认最多显示两行，超出部分省略，悬停显示完整内容；
- 其他字段默认单行省略，悬停显示完整内容；
- 保留横向滚动，不通过强制换行把每行撑成不受控高度；
- 使用紧凑表格密度，让同屏显示更多行和更多有效内容。

新增的五个催收字段进入列显示、排序、宽度偏好和导出字段白名单。是否支持服务端排序沿用现有字段排序规则；不为自由文本增加模糊排序或全文检索。

### 8.3 左侧导航

主系统默认侧栏宽度保持 228px。仅在应收账款模块内使用 196px，并同步内容区偏移和折叠状态，不能影响其他模块。

## 9. Modal 与 Drawer 关闭修复

修复范围是应收账款模块内全部 Modal 和 Drawer，包括新增、编辑、作废、回滚、字典、授权、附件和确认流程。

实现前先复现并定位共同根因。修复遵循以下统一契约：

- 右上角关闭、取消按钮、遮罩关闭和 Esc（允许时）都调用受控的 `onCancel`/`onClose`；
- 普通取消不触发表单提交或业务 mutation；
- 关闭后清理当前对象、确认阶段、临时文件、预览和表单错误；
- 再次打开显示当前业务对象或干净初始值，不残留上一次状态；
- 正在执行不可重复的提交时禁用重复提交，并按既有策略决定是否允许关闭；
- 必须保留明确需要跨步骤存在的导入预览状态，不能用全局重置误删有效流程。

优先修复共享的受控状态或事件路径，避免在每个按钮上堆叠互不一致的补丁。

## 10. API 与组件边界

本次在现有应收账款模块内扩展，不建立平行子系统：

- 现有 access resolver 返回 `canMaintainCollection` 及派生的催收维护能力。
- 现有台账创建、详情、列表和 PATCH 输入/输出增加五个恢复字段。
- 现有附件上传复用相同的台账写范围和新开关校验。
- 现有 references/facets 返回“单位”和导出分类选项所需的权限内实际值与 active 字典值。
- 现有导出服务增加预览、分类条件和选列参数，任务执行仍走共享的服务端查询构造器。
- 现有列偏好接口兼容读写 `widths`。
- 现有字典管理增加在用选项改名的预览/确认事务；不复制一份新的字典 API。
- 管理端复用已有台账表单、导入、导出、授权和列设置组件，将它们组织到新的“数据处理”页面。

所有新增请求体继续使用严格 schema；未知字段拒绝。服务端错误使用稳定业务码，前端显示可操作的中文信息。

## 11. 错误处理与安全边界

- 无权限、撤权、跨部门、只读及未启用开关：403，且不产生业务写入。
- revision、字典影响指纹或目标值冲突：409，要求刷新后重新确认。
- 导出零匹配、零选列或非法字段：400，不创建任务。
- 字典改名中任一台账历史、台账更新、选项更新或审计失败：事务回滚。
- 导出预览与正式任务都重新解析当前会话和权限；浏览器提供的部门、字段名和记录数都不可信。
- 私有附件继续在每次读取时按当前台账权限鉴权。
- 所有新增审计避免写入文件内容和不必要的完整自由文本，只保存支持追溯所需摘要。

## 12. 测试与发布门

实施采用测试先行。至少覆盖以下自动化检查：

### 12.1 权限与字段

- `canMaintainCollection = false` 的报账员不能修改六个字段或上传附件。
- 开关启用且部门 `canWrite = true` 时，可以修改项目状态和五个恢复字段并上传附件。
- 既有债权状态、清收责任人和催收备注权限在开关启用前后保持不变。
- 同一账号多个财务归属部门逐个执行读写范围；一个部门的写权限不能外溢到另一个部门。
- `canViewAll` 只扩大读取，不隐式授予写入。
- 只读、撤权、inactive 账号/人员和跨部门请求均拒绝。
- 每次字段修改有完整 before snapshot、递增 revision、原因和审计；并发旧 revision 返回 409。
- Excel 导入可识别五个恢复字段及其既有别名，预览、应用、冲突和历史行为与其他台账字段一致。

### 12.2 字典

- 四个恢复字段对应字典以及既有台账字典均可预览影响并事务性改名。
- 每条受影响台账都有独立 revision 历史，改名后列表、详情、筛选和导出立即显示新值。
- 影响集合变化、目标冲突、审计失败和中途异常全部回滚，不留下部分改名。

### 12.3 导出

- 选项是权限内实际值与 active 字典值的去重并集。
- 同条件多选为 OR，不同条件为 AND；结果不越过财务归属部门范围。
- 非空列默认选中，全空列默认不选，用户可改选，零选列被拒绝。
- 生成一个 XLSX、一个工作表、连续明细行、冻结表头和自动筛选。
- 零匹配不生成空文件；后台任务行数、列、SHA-256 和审计快照一致。
- 非法字段、伪造部门范围和无导出能力均由服务端拒绝。

### 12.4 页面与交互

- “数据处理”标签按能力显示，旧 URL 正确重定向，直接 URL 无法绕过权限。
- 新增成功后打开新台账详情；台账总览不再提供第二个新增入口。
- 单位筛选与服务端计数、分页一致。
- 列宽拖动后刷新仍保留；旧列偏好可兼容读取；宽度越界被归一化。
- 项目名称和客户名称最多两行且可查看全文，其他列保持紧凑单行。
- 应收账款模块侧栏为 196px，其他模块保持 228px。
- 在桌面和窄屏浏览器逐一验证应收账款模块的 Modal、Drawer 关闭路径、状态清理和重复打开。

### 12.5 正式发布门

在独立分支完成实现和针对性检查后，使用目标 Node.js 22 + PostgreSQL 16 环境，从干净数据库连续执行：

- Prisma schema 校验与全量迁移；
- 生产种子幂等检查；
- 新增专项测试、既有应收账款检查和真实 HTTP smoke；
- 全仓 typecheck、生产 build 和既有发布门；
- 浏览器桌面/窄屏人工验收；
- 数据库、文件、测试账号和测试端口零残留核对。

首次失败立即停止并记录，不把定向续跑包装为完整 FINAL。只有一次干净、连续的目标运行时 FINAL 通过后，才能书面批准合并和测试站切换；本设计批准本身不授权 push 或部署。

## 13. 实施顺序

为控制风险，实施计划按以下依赖顺序拆分：

1. 加法迁移、类型和访问能力。
2. 五个字段的 API、历史和报账员权限。
3. 字典改名事务与缓存失效。
4. 导出预览、分类条件、选列和单工作表生成。
5. “数据处理”路由与三个标签页。
6. 单位筛选、列宽偏好、长文本和侧栏宽度。
7. Modal/Drawer 根因修复及回归。
8. 专项、全量和目标运行时发布门。

每一步复用现有模块边界，避免为了本轮需求提前建设通用框架。
