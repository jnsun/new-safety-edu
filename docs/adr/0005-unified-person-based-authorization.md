# 统一以主系统人员承载跨业务授权

- 状态：已接受
- 日期：2026-09-21

## 背景

系统同时存在人员档案、登录账号、安全生产角色和应收账款授权。若业务授权绑定账号，换手机号、换微信、账号合并或尚未开通账号都会影响权限事实；若把人员和账号合成同一生命周期，又无法分别表达“员工仍在职但账号临时停用”和“人员离职后所有管理权限结束”。旧 `safety-web` 与 `new-safety-edu` 并行授权还会产生两个权限权威。

## 决策

`new-safety-edu` 是安全生产与应收账款当前权限的唯一权威，旧 `safety-web` 只作为规则和历史迁移参考，不再独立授权。

两类业务的角色、能力和数据范围都授予统一人员主档中的 active 正式员工，账号仅作为该人员登录和建立会话的凭据。人员可以没有账号并持有待激活授权；账号换绑、合并或重建不改变人员授权。一个人员最多关联一个当前有效账号，但人员状态和账号状态分别管理。

安全生产与应收账款继续作为两个独立权限域：角色不互相继承，公司管理员不因系统管理权获得财务业务数据，应收账款角色也不获得安全生产管理能力。所有终端访问经过服务端按人员、角色、能力、范围、有效期和业务对象状态鉴权，数据库不向终端用户直接开放。

日常管理以“人员档案”为唯一主入口，账号操作放在人员详情“账号与登录”中；独立队列只处理无法正常归属的登录与绑定异常。人员详情统一解释安全生产与财务权限，但新增授权仍从各业务入口发起。

## 后果

- 应收账款授权必须从 `accountId` 迁移到 `personId`，历史操作者账号仍保留追溯。
- 人员停用与账号停用产生不同结果，不能复用同一状态或接口。
- 角色、能力、范围和有效期必须成为服务端可解释的授权事实，页面隐藏不能代替鉴权。
- 账号合并不再需要迁移业务权限，只需保留登录身份与历史追溯关系。
- 前端需要取消正常账号独立工作台，保留异常处理队列。
- 迁移前必须扫描孤立账号、无人员角色、重复人员和不合法当前授权；不得自动猜测归属。
