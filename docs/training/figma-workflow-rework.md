## 1. 结论先行

本轮人工验收未通过的主要原因不是浏览器缓存，而是 **Figma 中的培训五步流程尚未在当前代码中实现并接入真实入口**。

当前系统具备课件、培训模板、题库、题目、试卷、培训批次和进度记录等底层对象及各自的维护页面，也具备真实下发 API；但实际操作仍分散在：

1. `/training-dashboard`：通用安全工作台；
2. `/courseware`：课件与培训模板；
3. `/questions`：题库、题目和试卷；
4. `/training`：单个弹窗内直接创建并下发；
5. `/records`：进度与记录。

当前 `/courseware` 虽显示“培训制作中心”，但只改了页头和视觉外壳，并没有 T03–T07 五步向导、向导级草稿状态、就地新建回填、准备度检查、覆盖人数预检、连续预览或下发结果页。因此应将其定性为 **仅界面/部分完成**，不能标记为 Figma 培训流程已跑通。

此外，现有 `POST /api/training-batches` 在一个数据库事务中创建批次和全部人员任务：成功即整批成功，任一异常即整批回滚。T08 设计的“275 人成功、3 人失败”部分成功结果 **没有现有后端语义支持**。下一轮不能只做一个展示页来模拟部分成功。

## 6. 关键业务边界核对

### 6.1 模板与本次安排

Figma T06 的边界与已确认业务规则一致：

- 培训模板保存：模板名称、培训类型、有序的已发布课件版本；
- 本次安排保存：是否考试、试卷、时长、合格分、最大次数、范围、截止时间；
- 重用模板时：必须重新确认考试设置，不能把旧批次考试配置静默带入新批次。

当前数据库 `TrainingTemplate`/`TrainingTemplateItem` 正好只保存名称、类型和课件版本顺序，考试配置在 `TrainingBatch`，不需要为了该边界新增迁移。

需要注意的现有历史保护：

- 下发时会为每名学员创建 `LearningProgress` 并记录具体 `coursewareVersionId`；
- 下发时会把试卷内容冻结到 `TrainingBatch.paperSnapshot`；
- 后续编辑模板或试卷不会改写已经发生的学习与考试事实。

但目前没有显式的“批次课件顺序快照”字段。`LearningProgress` 保存了版本引用，却没有 `sortOrder`；学员任务序列化也没有按模板顺序排序。若返工时确认历史顺序必须永久稳定，则需要最小迁移，例如在批次课件快照或学习进度上保存顺序。兼容方式应是：

1. 新批次写入显式顺序；
2. 旧批次继续读取现有引用，并按可恢复规则回填展示顺序；
3. 不更新或删除旧学习、考试、签字记录；
4. 迁移只增加字段/快照，不重建历史任务。

该项属于 **待业务确认**，实施前需确认是否把“下发时课件顺序不可变”作为正式历史事实。

### 6.2 T08 部分成功与当前事务

当前手工下发实现：

1. 服务端验证模板、试卷、范围和人员；
2. 在一个 `prisma.$transaction` 内创建 `TrainingBatch`；
3. 在同一事务中逐人创建 `TrainingAssignment`、`LearningProgress` 和通知；
4. 任一创建失败会使整个事务回滚。

因此现有真实语义是 **整批原子成功或整批失败**。T08 画板中的部分成功数据只能视为设计状态示例，不能直接照搬。

建议的最小方案是保留原子语义：

- 预检阶段把可预见的人员问题全部列出；
- 用户确认的目标集合在提交时再次核验；
- 若关系发生变化，整批阻止并要求刷新预检；
- 结果页只显示真实的整批成功或整批失败；
- 不展示虚构的“成功 N、失败 M”。

只有用户明确确认业务必须支持部分成功时，才应另行设计：子任务独立事务、失败重试、重复下发去重、结果持久化和审计。这不是纯前端改造。

### 6.3 预览、预检和正式下发的一致性

当前三个动作没有共用同一份服务器可验证配置：

- 预览：只有单课件本地预览；
- 人数预检：不存在；
- 正式下发：直接把表单发送到 `POST /api/training-batches`。

返工时应让三者都消费同一个前端 `TrainingDraft`，并由服务端 preflight 返回：

- 规范化后的配置摘要或哈希；
- 当前包含/排除人数与原因；
- 课件发布和作用域状态；
- 试卷可用性和题量；
- 有效期较短的一次性预检标识。

正式下发若发现草稿、人员范围或依赖资产已变化，应 fail closed，要求重新预检，不能静默按新数据下发。
