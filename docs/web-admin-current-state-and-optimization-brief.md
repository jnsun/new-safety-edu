## 1. 本轮优化目标

本轮有两个重点：

1. 优化培训内容的制作和下发流程，解决课件、培训模板、题库、题目、试卷、培训安排分散且操作链路不连贯的问题。
2. 调整登录后的系统入口：安全生产管理系统和财务应收账款系统是两个并列系统，不再把应收账款仅作为安全系统九宫格中的一个普通模块。

本轮首先优化 Web 后台信息架构和操作体验，尽量复用现有接口与数据模型。不要为了改页面重新设计数据库，也不要破坏小程序当前学习、考试、签字流程。

---

## 2. 当前技术与业务边界

- 单仓库：pnpm workspace。
- Web 管理端：React、Vite、TypeScript、Ant Design、React Router、TanStack Query。
- API：Fastify、TypeScript、Zod、Prisma。
- 数据库：PostgreSQL。
- Web 与 API 同域，Web 只通过 `/api` 访问业务数据。
- 统一人员、账号、组织、项目主档；安全业务和财务业务不重复建立人员账号体系。
- 登录会话、角色范围、私有文件和审计均由服务端控制。
- 当前正式安全业务模块是：
  - 培训教育；
  - 野外项目报送；
  - 资质证照管理。
- 人员与组织管理是三个安全业务模块共用的基础主档模块。
- 应收账款是同一平台内的原生财务系统，复用统一登录和基础人员身份，但使用独立的财务权限模型。
- 系统只记录培训、证照、项目、月报和财务事实，不产生“可上岗”“禁止上岗”等自动资格结论。

## 3. 当前 Web 登录与入口现状

### 3.1 已实现

- 微信网站应用扫码登录为主入口。
- 用户名和密码登录作为备用入口。
- 首次临时密码登录后强制修改密码。
- 修改密码、管理员重置密码、忘记密码验证码流程。
- HttpOnly Cookie 会话、refresh session、退出当前会话、退出全部设备。
- 登录失败次数限制和临时锁定。
- 账号停用、角色撤销后会话失效。
- 页面右上角显示当前人员姓名、主部门和管理角色摘要。
- 登录后当前统一跳转到 `/`。
- `/` 当前显示安全生产管理平台九宫格。
- 当前只有具备应收权限的人会在九宫格第九格看到“应收账款管理”；没有应收权限的人在同一位置看到“事故事件管理（待规划）”。
- 应收账款已有独立的服务端权限查询接口 `/api/receivables/access`，直接访问财务路由时也会再次鉴权。

### 3.2 当前缺口

- 尚未实现“登录后按系统权限自动分流”。
- 只有安全系统权限的人，当前仍会先看到统一九宫格，而不是直接进入安全系统。
- 只有财务权限的人，当前也不会直接进入应收账款系统。
- 同时具备安全和财务权限的人，当前没有独立的“双系统选择页”。
- 安全系统入口卡片和应收账款入口混在同一九宫格中，系统层级与业务模块层级不够清晰。
- 当前前端九宫格会固定显示多个安全模块入口；是否真的有权操作主要依赖各 API 的服务端鉴权，缺少统一的“可进入安全系统”能力结果。

## 4. 安全生产管理系统当前已实现功能

### 4.1 人员与账号

已实现：

- 人员档案列表、搜索、类型和状态筛选。
- 按部门分组查看人员，默认部门列展示。
- 新建、编辑、补录、停用、重新启用人员。
- 仅对完全无业务引用的误建空档案允许删除；其他人员保留历史。
- 批量选择、批量设置主部门、批量停用预检查。
- 人员 Excel/CSV 导入，支持预检查、冲突提示、组织匹配、确认写入和结果统计。
- 人员照片 ZIP 导入和受控私有存储。
- 身份证加密保存、hash 去重、默认脱敏展示、授权后查看完整信息。
- 人员详情页已经按页签展示：
  - 基本档案；
  - 账号与登录；
  - 组织与权限；
  - 项目关系；
  - 证照；
  - 培训记录；
  - 申请与变更；
  - 操作记录。
- 创建账号或发起账号开通。
- 修改用户名、重置临时密码、启用和停用账号。
- 解除用户名密码、手机号或微信登录方式。
- 账号合并、人员档案合并申请。
- 账号和人员异常处理。
- 管理角色授予、撤销、待账号激活授权和范围校验。
- 审核中心处理绑定、注册、资料变更、部门调动、项目加入/退出、账号开通/找回、账号合并、人员合并等申请。
- 敏感资料按公司、组织或项目范围生成短时、一次性下载文件并保留审计。

- 组织内人员、职责权限、负责项目和变更记录查看。
- 项目新建、编辑、暂停、恢复和结束。
- 项目责任实体、项目管理员和项目成员维护。
- 项目成员批量加入、申请审核、取消和结束关系。
- 项目概览、成员、管理员、加入申请、培训关联和变更记录页签。

### 4.3 培训管理首页

### 4.4 课件

已实现三类课件：

1. 图文课件；
2. 单文件 HTML 交互课件；
3. 结构化互动课件。

当前能力：

- 新建、编辑、发布和删除课件。
- 公司、组织、项目适用范围。
- 课件发布权限授权。
- 已被历史任务使用的内容在后台保留历史事实，日常列表显示当前内容。
- HTML 文件通过私有文件机制和受控 viewer 使用。
- 结构化课件可维护课程摘要、学习目标、预计时长、单元和顺序。
- 结构化内容块包括：
  - 图文知识卡；
  - 应该 / 不应该；
  - 操作步骤；
  - 随堂题；
  - 情境选择；
  - 三点总结。
- 内容块支持添加、编辑、复制、删除和上下移动。
- 结构化课件提供手机效果预览。
- 支持私有图片素材。
- 支持下载空白 XLSX、示例 XLSX、JSON 示例和 JSON Schema。
- 支持 XLSX、XLSM、JSON、ZIP 批量导入。
- 导入具备“上传 → 预检确认 → 导入结果”流程，并区分新增、新版本、冲突和无效数据。
- 支持按 XLSX、JSON、ZIP 导出结构化课件。
- 有未保存内容时阻止误关闭或误跳转。

## 6. 已有代码但仍依赖外部配置或人工验收的能力

以下不能简单标为“完全完成”：

### 6.1 Web 微信扫码登录

- 页面和 API 已有。
- 需要微信开放平台“网站应用” AppID、AppSecret 和正式回调域名配置。
- AppSecret 只能放在服务器环境变量中。
- 仍需分别在测试和生产环境做真实扫码回归。

### 6.2 短信验证码

- 验证码生成、6 位验证码、5 分钟有效、60 秒重发限制、错误次数限制、验证后消费、找回密码和修改手机号业务流程已经存在。
- 当前 API 通过 `SMS_SEND_ENDPOINT` 和 `SMS_SEND_TOKEN` 调用通用短信网关。
- 当前仓库尚不是直接调用腾讯云短信 SDK 的完整实现。
- 腾讯云签名、模板、SecretId/SecretKey、安全日志和回执仍需按正式短信接入方案完成并验收。
- 短信不应成为独立登录方式，只用于绑定、换绑、手机号验证和密码找回。

### 6.3 微信订阅消息

- 授权入口和 outbox 已有。
- 是否真实发送取决于微信模板 ID、用户授权、额度和服务器配置。
- 发送失败不能阻断系统内消息。

### 6.4 每日挑战

- 代码已经具备。
- 每个环境需要实际启用挑战题；测试站配置不会自动同步到生产站。

### 6.5 微信小程序和真机

- Web 后台代码完成不代表微信真机流程自动通过。
- 登录绑定、学习恢复、情境题、考试、签字、私有文件和管理入口仍需用微信开发者工具和真机持续验收。

这些是待规划方向，不应在本轮为了填满九宫格而仓促建设。

### 7.3 培训内容的一体化制作工作台

当前课件、培训模板、题库、题目、试卷和培训下发都能分别操作，但尚未形成一个连续的“培训方案制作向导”或“一站式工作台”。这是当前最明显的体验缺口。

### 7.4 当前版本明确不建设的范围

除非另行确认，不要在本轮加入：

- 自动上岗资格或禁止上岗结论；
- 电子资格凭证和通行二维码；
- 证照自动准入判断；
- GPS、现场照片核验；
- 离线学习、离线考试和离线同步；
- 复杂规则引擎、流程设计器和 BI 大屏；
- Word/PDF 自动解析为课件；
- 复杂 PDF 排版引擎；
- 把证照年度培训自动等同于培训教育任务。

## 8. 当前培训制作流程及主要问题

### 8.1 当前真实流程

管理员要完成一次带考试的培训，通常需要：

1. 在“课件与模板”创建课件；
2. 编辑课件内容；
3. 发布课件；
4. 创建培训模板；
5. 在模板中选择已发布课件并排列顺序；
6. 进入“题库与试卷”；
7. 新建或选择题库；
8. 新建、编辑或批量导入题目；
9. 新建固定试卷或随机试卷；
10. 进入“培训安排”；
11. 选择培训类型、模板、范围、截止时间和考试参数；
12. 确认下发；
13. 再到“进度与记录”查看结果。

### 8.2 不流畅的原因

- 业务目标是“建立并下发一次培训”，但页面按数据库对象拆分，管理员必须理解课件版本、模板、题库、题目、试卷等技术关系。
- 三个一级页面之间来回切换，缺少清晰的当前位置、完成度和下一步。
- 创建培训模板时只能从已发布课件列表选择，缺少就地新建、编辑、预览和发布。
- 创建试卷时需要提前准备题库和题目，缺少从培训制作流程中直接创建题目或随机规则的入口。
- “培训模板”和“考试模板”概念容易混淆。系统实际对象是“培训模板”和“试卷”，应统一用词，不再使用模糊的“考试模板”。
- 批量导入存在于不同弹窗，但入口、模板说明、预检结果和错误处理风格不完全一致。
- 缺少“这个培训现在能不能下发”的总检查，例如：课件是否发布、题量是否足够、考试是否必选、范围是否有 active 人员。
- 缺少学习者视角的整体预览：管理员不能在同一处完整预览“任务详情 → 课件顺序 → 考试要求 → 签字要求”。
- 下发前缺少预计覆盖人数、排除人数和排除原因汇总。
- 操作成功后虽然数据已保存，但对“下一步去哪”提示不足。
- 高级批量能力和普通管理员的日常操作混在一起，页面按钮较多，认知负担较大。

## 9. 培训模块建议的目标信息架构

### 9.1 保留底层模型，重做上层操作路径

不要删除现有 `Courseware`、`TrainingTemplate`、`QuestionBank`、`Question`、`ExamPaper`、`TrainingBatch` 等模型。历史培训、考试和签字依赖这些对象和快照。

前端增加一个面向业务目标的“培训制作中心”，底层仍调用现有 API：

```text
培训教育
├─ 培训首页
├─ 培训制作中心
│  ├─ 我的培训方案
│  ├─ 课件库
│  ├─ 题库
│  └─ 试卷库
├─ 培训安排
├─ 进度与记录
└─ 报表与设置
```

“培训制作中心”不是新增一套平行业务数据，而是对现有课件、模板、题库和试卷提供统一操作界面。

### 9.2 新建培训方案向导

建议提供五步向导：

#### 第一步：基本信息

- 培训名称；
- 培训类型；
- 适用范围；
- 简要说明。

选择培训类型后立即解释规则：

- 三级安全教育：仅正式员工，必须考试；
- 项目入场教育：项目成员，必须考试；
- 日常/年度培训：考试默认关闭；
- 变化内容培训：考试默认关闭。

#### 第二步：学习内容

- 从课件库选择课件；
- 直接拖动或用上下按钮调整顺序；
- 可在侧边抽屉中快速新建课件；
- 可就地编辑尚未发布的课件；
- 显示课件类型、状态、时长和适用范围；
- 支持学习者手机视角预览。

#### 第三步：考试设置

- 清晰的“需要考试”开关；
- 对三级教育和项目入场教育强制开启且说明原因；
- 可以选择已有试卷；
- 也可以直接选择“从题库随机抽 N 题”；
- 可在当前步骤新建题库、导入题目或建立试卷，不要求离开向导；
- 显示可用题量、抽题量、合格分、时长和最大次数；
- 题量不足时在下发前阻止并说明。

#### 第四步：保存与预览

- 将以上内容保存为可复用培训模板；
- 显示任务详情预览；
- 显示课件顺序、考试规则、签字要求和项目确认要求；
- 显示“内容准备度”检查结果。

#### 第五步：选择范围并下发

- 公司管理员：全部组织、部分经营实体/部门或某个项目；
- 组织负责人/管理员：本人组织全体 active 人员；
- 项目管理员：本人项目全体 active 成员；
- 显示预计下发人数；
- 显示停用人员、范围不符人员等排除人数和原因；
- 设置截止时间；
- 最终确认后下发。

### 9.3 专业库管理仍需保留

向导用于日常快速制作，原有专业维护能力继续保留：

- 课件库：批量导入导出、发布授权、结构化编辑；
- 题库：大批量导入、搜索、筛选、编辑和删除；
- 试卷库：固定试卷、随机试卷、编辑和删除；
- 培训模板：复用、复制、编辑和停用。

但专业库页面应减少同屏按钮，使用“主要操作 + 更多操作”分层。

### 9.4 统一状态和文案

统一使用以下名称：

- 课件；
- 培训模板或培训方案；
- 题库；
- 题目；
- 试卷；
- 培训安排；
- 培训任务。

不要再使用含义不清的“考试模板”。

建议统一内容状态：

- 草稿；
- 可用/已发布；
- 已停用；
- 被历史记录引用。

“删除”按钮必须先由服务端判断：

- 未被引用的数据可以删除；
- 已被正式培训或考试引用的数据不能破坏历史，只能停用或从日常列表隐藏；
- 页面必须显示不能删除的具体原因。

### 9.5 下发前准备度检查

下发按钮旁增加检查清单：

- 至少一个可用课件；
- 所有课件已发布或可供当前范围使用；
- 必须考试的培训已选择有效试卷；
- 随机试卷可用题量足够；
- 固定试卷至少一题且总分有效；
- 培训范围合法；
- 范围内存在 active 人员；
- 截止时间合理；
- 自动下发所需默认配置完整。

检查失败时不得“点击无反应”，必须在字段旁和页面顶部同时显示明确原因。

### 9.6 批量导入体验统一

课件和试题导入统一使用：

```text
下载模板
→ 选择文件
→ 文件解析
→ 预检查
→ 显示可导入/冲突/错误
→ 用户确认
→ 正式写入
→ 结果页
```

统一要求：

- 上传后立即显示正在解析；
- 失败必须显示文件级错误或具体行号；
- 不允许静默跳过；
- 模板中提供字段说明和匿名示例；
- 结果可下载错误明细；
- 关闭弹窗再打开时不能误显示上一次成功状态；
- 重复确认必须幂等。

## 10. 双系统登录入口正式需求

### 10.1 两个并列系统

登录后可进入的系统只有两个顶层入口：

1. **安全生产管理系统**；
2. **财务应收账款系统**。

安全系统内部继续包含培训教育、野外项目报送、资质证照、人员与组织管理，以及待规划安全模块。应收账款不再作为安全系统九宫格中的第九个业务模块。

### 10.2 跳转矩阵

| 安全系统权限 | 应收账款权限 | 登录后行为 |
|---|---|---|
| 有 | 无 | 直接进入安全生产管理系统首页 |
| 无 | 有 | 直接进入财务应收账款系统首页 |
| 有 | 有 | 显示系统选择页，由用户选择进入哪个系统 |
| 无 | 无 | 显示“当前账号没有可用的 Web 系统权限”，只提供退出和联系管理员提示 |

只有同时具备两个系统权限的人才显示选择页。单系统人员不能多走一步。

### 10.3 安全系统权限判定

建议由服务端统一返回，不允许前端自行猜测。

当前至少以下有效管理角色可以构成安全系统访问能力：

- `company_admin`；
- `org_leader`；
- `org_admin`；
- `project_admin`；
- `field_reporter`。

具体进入后的模块和数据范围仍按现有角色与 scope 判断。普通人员的学习端是微信小程序，不因为拥有 active 账号就自动进入 Web 安全管理后台。

### 10.4 财务系统权限判定

直接复用服务端现有 `ReceivablesAccess.canEnter` 权威结果：

- 财务资产部负责人；
- 财务管理员；
- 获授权报账员；
- 获授权只读人员；
- 财务资产部 active 普通成员的默认只读能力。

公司管理员身份本身不自动等于财务数据访问权限；只保留现有未配置状态下的紧急恢复能力。

### 10.5 建议的服务端契约

可以扩展 `/api/auth/me`，或增加 `/api/auth/system-access`。建议返回：

```json
{
  "data": {
    "safety": {
      "canEnter": true,
      "defaultPath": "/safety"
    },
    "receivables": {
      "canEnter": true,
      "defaultPath": "/receivables"
    }
  }
}
```

要求：

- 结果必须由服务端根据当前账号、人员状态、当前有效角色和财务授权实时计算；
- 账号停用、人员停用、角色撤销或财务授权撤销后下一次请求立即生效；
- 不允许仅根据前端菜单是否显示来判断权限；
- 直接输入 URL 仍必须由服务端拒绝越权请求；
- 前端不得通过 localStorage 伪造系统权限。

### 10.6 路由建议

建议将层级明确为：

```text
/login                 登录
/systems               仅双权限用户看到的系统选择页
/safety                 安全生产管理系统首页
/safety/...             安全系统各模块
/receivables            应收账款系统首页
/receivables/...        应收账款各页面
/no-system-access       无 Web 系统权限提示
```

为了降低本轮改动风险，也可以暂时保留现有安全模块路径，但必须有统一入口解析和路由守卫；不要为了路径美观一次性重写全部业务路由。

### 10.7 系统选择页

只显示两张清晰的大卡片：

- 安全生产管理系统：人员、组织、项目、培训、月报和证照；
- 财务应收账款系统：合同应收、开票、回款和催收台账。

页面显示当前登录人姓名、部门和权限摘要，并提供退出登录。

双权限用户进入某个系统后，右上角增加“切换系统”。单权限用户不显示该按钮。

本轮不默认记住上一次选择，避免共用电脑或权限变化后自动进入错误系统。以后如要增加偏好，也必须先重新获取服务端权限。

### 10.8 安全系统九宫格调整

进入安全系统后显示以下九项：

1. 培训教育；
2. 野外项目报送；
3. 资质证照管理；
4. 安全责任制（待规划）；
5. 人员与组织管理；
6. 隐患排查治理（待规划）；
7. 安全检查（待规划）；
8. 应急管理（待规划）；
9. 事故事件管理（待规划）。

应收账款不再替换“事故事件管理”卡片。

## 12. 非协商业务约束

- 三级安全教育和项目入场教育必须考试。
- 日常/年度培训和变化内容培训默认不考试。
- 培训按完整组织或完整项目下发，不开放任意个人勾选下发。
- 已停用人员不生成新任务。
- 自动下发必须幂等。
- 客户端不能自行判定学习完成、考试通过、签字完成或权限范围。
- 正确答案和评分规则不能在考试开始前返回客户端。
- 已发生的学习、考试、签字、项目确认和财务历史不能因编辑当前模板而被覆盖。
- 删除当前可维护对象不能破坏历史快照和审计。
- 应收账款金额和权限继续使用现有服务端财务模型，不根据安全管理角色在前端推断。
- 不能通过隐藏按钮代替服务端鉴权。
- 不修改小程序 test/prod 环境隔离和生产保护。

## 13. 验收标准

### 13.1 双系统入口

- 安全单权限账号登录后直接进入安全系统。
- 财务单权限账号登录后直接进入应收账款。
- 双权限账号登录后只看到两个系统选项。
- 无权限账号进入无权限提示页。
- 双权限用户可以安全切换系统。
- 财务权限撤销后，旧页面下一次请求被拒绝。
- 安全角色撤销后，旧页面下一次请求被拒绝。
- 直接输入无权系统 URL 不能越权读取数据。
- 页面刷新后仍保持正确系统和会话。
- 退出登录后两个系统均不可访问。

### 13.2 培训制作中心

- 新管理员无需先理解所有数据库对象，也能按向导完成一项培训。
- 可以从向导内创建或选择课件。
- 可以从向导内选择固定试卷或随机组卷规则。
- 必须考试规则不能被关闭。
- 可选考试默认关闭。
- 下发前能看到完整预览、覆盖人数和所有阻塞原因。
- 任一保存或下发失败都会显示明确错误，不出现“点击没有反应”。
- 返回上一步不丢失已填写内容。
- 正式下发只发生一次，重复点击不能重复生成任务。
- 原有课件导入、题目导入、自动下发、撤回、进度、报表和小程序学习流程不回退。

### 13.3 最小回归

- Web 微信扫码登录和用户名密码登录。
- `/auth/me`、刷新、退出和首次改密。
- 人员、组织、项目范围权限。
- 课件新建、编辑、发布、导入和删除约束。
- 题库、题目、试卷新建、编辑、删除和导入。
- 培训创建、下发、编辑名称/截止时间和撤回未完成任务。
- 学员学习、考试恢复、补学、锁定/解锁、签字和记录。
- 五类报表。
- 应收账款只读、报账员、财务管理员和负责人四类权限。
- Admin production build、API build 和现有针对性检查通过。

## 15. 给实施 AI 的执行要求

1. 先核对当前 `main`、`origin/main` 和工作区，不覆盖其他并行开发内容。
2. 先画出现状路由和目标路由，再修改代码。
3. 先实现服务端系统访问能力，再做前端跳转，不能只写前端判断。
4. 培训制作中心优先复用现有 API 和组件，不另建一套平行课件、题库或培训表。
5. 允许调整 Web 信息架构，但不修改已经确认的培训业务规则。
6. 对实际代码不支持的交互明确列出缺口，不用假数据伪装完成。
7. 使用匿名或隔离数据验证，不直接改生产数据。
8. 完成后先报告修改文件、接口、migration、检查结果和 Git 状态；未经确认不要自动部署生产。
